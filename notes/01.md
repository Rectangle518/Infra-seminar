
## 1. 从 HPC 到 AI Infra

### 1.1 “3D并行”

**3D并行**是一种在训练GPT这类超大规模AI模型时，将**数据并行、流水线并行和张量（模型）并行**这三种策略组合起来使用的“组合拳”。可以把它想象成一个立体的三维网格，其中的每个维度都负责解决一个特定的问题，共同挑战单个GPU装不下、算得慢的困境。

它的核心思想，就是把“数据量大”、“模型太大装不下”、“层数太深算得慢”这三个问题，分别交给三种并行策略去解决：

*   **数据并行 (Data Parallelism)**：负责“多线开工，加速迭代”。把训练数据切分成多份，交给多个GPU同时处理。每个GPU都有一份完整的模型副本，各自算完后同步梯度，一起更新模型。这主要解决了**数据量大**和**训练速度慢**的问题。
*   **流水线并行 (Pipeline Parallelism)**：负责“接力合作，装下大模型”。把模型按层切分成几个阶段，不同阶段放在不同的GPU上。数据像在流水线上一样，一个阶段算完传给下一个阶段。这主要解决了**模型太深，单卡装不下**的问题。
*   **张量并行 (Tensor Parallelism)**：负责“拆分巨人，精细计算”。把模型内部某一层（比如一个巨大的矩阵）切分成小块，分散到多个GPU上共同完成这一层的计算。这主要解决了**单层计算量或参数过大**的问题。

> [!tip]
>
> **怎么理解 “3D”？**
>
> “3D”是指一个由这三种并行策略构成的**三维并行计算网格**。要搭建这个网格，通常至少需要 **8个GPU**（因为每个维度至少需要2个GPU）。
>
> 这就像是在一个三维空间里，长、宽、高分别对应一种并行策略。每个GPU都处在这个网格中的一个坐标点上，同时处理着属于自己的那一小块数据和模型参数。

这种组合使得训练万亿参数级别的巨型模型成为可能，像Megatron-Turing等模型就应用了类似的策略。目前，像DeepSpeed和Colossal-AI这类知名的深度学习框架，都提供了对3D并行的支持。

不过，它最大的挑战在于**通信开销**和**负载均衡**。GPU之间需要疯狂地“聊天”来同步数据和传递中间结果，如果网络不够快或者任务分配不均匀，效率就会大打折扣。因此，实际的工程优化非常复杂，需要精细地调整和设计。

## 2. CUDA 编程模型

### 2.1 Warp内数据交换

`__shfl_down_sync` 是 CUDA 中用于**线程束内（Warp）高效数据交换**的核心函数，可以把它理解成一个"向下"的数据移动指令。

它最主要的优势是让线程束内的线程能**直接读取其他线程寄存器里的值**，整个过程完全不需要使用共享内存，因此延迟极低且不消耗额外的内存带宽。可以把线程束想象成一排（32个）紧挨着的工人，这个函数就是让每个工人从"下面"某个工人手里接过数据。

#### 函数原型与参数解读

`__shfl_down_sync` 是旧版 `__shfl_down` 的升级替代品，在 CUDA 9.0 及更新版本中**推荐使用新版本**。它的函数签名如下：

```c++
T __shfl_down_sync(unsigned mask, T var, int delta, int width = warpSize);
```

它的参数需要特别留意：

*   **`mask` (关键的新增参数)**: 这是一个**参与掩码**，用于指明当前线程束中**哪些线程**会一同参与这个洗牌操作。为了达到和旧版本相同的效果，可以传入 `0xFFFFFFFF` 表示线程束内所有线程都参与。从 CUDA 9.0 开始，**必须**使用带 `_sync` 后缀的函数并正确设置掩码，否则结果未定义，这也是代码迁移到新架构的关键要求。

*   **`var`**: 这是当前线程想要"交出去"的变量值。每个线程都会把自己的 `var` 拿出来，同时接收目标线程的 `var`。

*   **`delta`**: 这是**向下的偏移量**。线程会从 **`当前 lane ID + delta`** 这个位置上的线程那里获取数据。

*   **`width` (可选)**: 这个参数定义了参与操作的"子线程束"宽度，它必须是2的幂次方，且小于等于32。比如 `width=16`，线程束会被分成两组，每组16个线程独立进行数据交换，互不干扰。

#### 核心工作方式

假设一个线程束有 32 个线程（lane ID 0-31），当某个线程调用 `__shfl_down_sync(mask, var, 2, 32)` 时，通信方式如下：

*   **对于 lane 0**: 它会尝试从 `lane (0+2)=2` 获取数据，所以 `lane 0` 的 `var` 最终会变成 `lane 2` 提供的值。
*   **对于 lane 2**: 它会尝试从 `lane (2+2)=4` 获取数据。
*   **...依此类推**。
*   **对于 lane 30 和 lane 31**: 由于 `30+2=32` 和 `31+2=33` 都超出了线程束的范围，**数据不会循环回来**，这两个线程的 `var` 将**保持原值不变**。

#### 主要用途

`__shfl_down_sync` 经常用在需要线程束内协作规约（Reduction）或前缀和（Prefix Sum）的算法中。比如，想要快速求出线程束内所有线程数据的总和，就可以用一个循环，`delta` 从 16 逐渐减到 1，每次调用都让数据像漏斗一样"向下"累加，最终 lane 0 就得到了总和。相比使用共享内存，这种方法指令更少、延迟更低，并且减少了对共享内存这一宝贵资源的压力。

总结一下，`__shfl_down_sync` 是一种强大且高效的线程间通信工具。理解并正确使用它（特别是注意 `mask` 参数和边界线程的行为）是编写高性能 CUDA 代码的关键一步。

### 2.2 Block 内的共享内存

`__shared__` 是一个**CUDA C++ 中的变量修饰符**，用来声明共享内存（Shared Memory）中的变量。

```cpp
__shared__ float sharedData[128];
```

当你在核函数（Kernel）里这样声明一个变量时，这个变量**不会被分配在常规的全局内存（Global Memory，也就是显存）**中，也不会存在每个线程私有的寄存器里，而是被分配在**流式多处理器（SM）内部一块非常特殊的高速缓存**上。

> [!tip]
> Block 是运行在 SM 上的。 一个 SM 可以同时处理一个或多个 Block（取决于资源），当一个 Block 被调度到一个 SM 上后，就会一直在该 SM 上运行直到结束。
> 
> 同一个 Block 内的所有线程，只在同一个 SM 上运行，所以它们才能通过 __shared__ 共享内存通信。

#### 它的关键特性

1. **极快的访问速度**：共享内存位于 GPU 芯片内部，其访问延迟只有全局内存的 **1/100 甚至更低**，速度堪比一级缓存（L1 Cache）。你手动将数据搬到这里，就能极大减少对慢速全局内存的访问。

2. **线程块内全局可见**：它被**整个 Block**里的所有线程共享。同一个线程块内的线程，都能自由读写这块共享内存中的数据（但要注意，线程束内不同线程访问时可能会产生内存排头冲突，即 Bank Conflict）。

3. **生命周期短**：它的生命周期**仅限于所在的线程块**。一旦该线程块执行完毕，这块共享内存就会被释放，分配给下一个线程块使用。

#### 常见用法

`__shared__` 最经典的用法是**对数据进行分块（Tiling）和重用**。例如在矩阵乘法中，将矩阵的一块数据（Tile）从全局内存加载到共享内存，然后线程块内的所有线程反复使用这块数据来计算，最后写回全局内存。这样，对全局内存的大量重复访问，就被对共享内存的快速访问替代了，性能常常能有数量级的提升。

#### 使用注意事项

1. **容量有限**：共享内存是宝贵的稀缺资源。现代 GPU 的每个 SM 通常只有几十到一百多 KB 的共享内存。如果声明或使用了超出硬件限制的大小，核函数将无法启动。
2. **需手动管理**：不同于自动缓存的 L1，共享内存需要你显式地用 `__syncthreads()` 等函数进行线程间同步，避免数据竞争。
3. **动态声明**：如果你想在运行时才知道数组大小，可以使用 `extern __shared__ int dynamicArray[];` 这种动态声明方式，在启动核函数时通过第三个执行配置参数指定字节数。

### 2.3 Thread Block Cluster

`Thread Block Cluster` 是 CUDA 编程模型中，在传统的**线程 (Thread) -> 线程块 (Block) -> 网格 (Grid)** 层次之上，新增加的一层抽象。它是在 **NVIDIA Hopper 架构 (计算能力 9.0)** 及之后版本中引入的一个重要特性。

#### 它是什么？
一个 **Cluster 是由一组线程块 (Thread Block) 构成的**。你可以把它想象成一个“线程块的集合”。它的核心特点是：
*   **同处一室，实时协同**：Cluster 内的所有线程块，会被**保证同时调度**在同一个 **GPC（图形处理簇）** 内的 SM（流式多处理器）上运行。这意味着它们可以真正地同步并高效通信，而传统CUDA模型中不同的Block之间是无法保证同时运行的。

#### 它解决了什么问题？
传统 CUDA 模型中，不同线程块之间是**相互独立**的，无法直接通信，也无法保证执行顺序。如果需要跨块交换数据，通常只能通过**全局内存 (Global Memory)** 进行，这速度较慢。

`Thread Block Cluster` 的引入就是为了解决这个问题，它实现了：
1.  **跨块共享内存访问**：Cluster 内的线程块可以直接读写彼此的 **共享内存 (Shared Memory)**，这一特性被称为**分布式共享内存 (DSMEM)**，访问延迟与访问本地共享内存相当，远快于全局内存。有评测显示，利用Cluster进行数据传递，相比使用全局内存**最多可以快 2.3 倍**。
2.  **集群级同步**：引入了 `cluster_sync()` 这样的同步原语，可以让整个 Cluster 内的所有线程块在某个点上同步，协调工作。

#### 与 TMA 的黄金搭档
Cluster 的强大功能与 **TMA（张量内存加速器）** 的 **Multicast（多播）** 功能结合后，能发挥出惊人的效果。

在矩阵乘等场景中，不同线程块可能需要同一份输入数据。传统方式下，每个块都要从全局内存读一次。而有了 TMA Multicast，硬件可以**只读取一次数据，然后同时发送给 Cluster 内的多个线程块**，大幅减少了全局内存的访问量。

#### 应用场景举例
*   **Halo Exchange（边界数据交换）**：在图像处理或物理模拟的模板计算（Stencil）中，每个数据块需要来自相邻块的边界数据。使用 Cluster，可以直接通过 DSMEM 从邻居的共享内存中读取，无需经过全局内存。
*   **高性能矩阵乘 (GEMM)**：通过 Cluster 协同工作并利用 TMA Multicast 加载数据，可以显著提升矩阵乘法的性能。
*   **动态负载均衡 (Work Stealing)**：在 Blackwell 架构中，Cluster 还配合了“集群启动控制”功能，允许空闲的线程块“偷取”其他尚未执行块的任务，实现更高效的负载均衡。

#### 使用要点
1.  **硬件要求**：需要**计算能力 9.0 及以上**的 GPU（如 Hopper, Blackwell 架构）。
2.  **集群大小**：一个 Cluster 包含的 Block 数量是有限制的，**最大通常为 8 个**（部分架构和配置可支持到 16 个）。启动核函数时需要将 `cluster` 作为额外的维度参数传入。
3.  **资源与性能权衡**：使用 Cluster 会强制将多个 Block 调度在同一个 GPC，可能会**降低SM的占用率（Occupancy）**。建议从较小的集群（如2-4个Block）开始测试。另外，过大的集群尺寸也可能带来超过 **20%** 的执行时间开销。
