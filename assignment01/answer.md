
## 1. 为什么要用 GPU

### 1.1 

(a) **错**。标称算力（TFLOPS）是吞吐量指标，延迟由时钟周期和流水线深度决定，5 GHz CPU 的单条指令延迟通常远低于 GPU。

(b) **对**。HBM 的标称带宽是理想连续传输下的峰值，随机小粒度访问会因 bank 冲突、寻址开销等导致实际有效带宽大幅下降。

(c) **对**。严格串行迭代中每步依赖上一步，无法并行化，瓶颈在于单步延迟而非算力吞吐，换更强 GPU 几乎无提升（除非单步计算本身可并行）。

(d) **错**。算力（FLOPS）是每秒操作次数，其倒数是平均每周期吞吐时间，并非单次运算的延迟（延迟通常指从输入到输出完成的时间，远大于这个倒数值）。

### 1.2 

总计算量 10e12 FLOP（1 TFLOP），放在一块标称 **1000 TFLOPS**（即 10¹⁵ FLOP/s）的 GPU 上，**纯数学时间** = 10e12 / 10e15 = **0.001 秒 = 1 毫秒**。

这个计算没有错，但它算的是**吞吐量极限**。

为什么“严格在线串行算法”做不到？

（1）从“吞吐”角度看：流水线根本“喂不饱”

- GPU 的 1000 TFLOPS 是靠 **上万个计算核心同时干活** 堆出来的。
- 要喂饱这些核心，需要**海量的并行任务**（比如矩阵乘法里成千上万个独立的乘加操作）。
- 但**严格串行**意味着：**第 N 步算完之前，第 N+1 步的输入数据根本不存在**。
  - 于是你只能**一个核心干活，其余 9999 个核心空转**。
  - 此时实际有效吞吐 ≈ **单核性能**（大概几 TFLOPS 都不到），而不是 1000 TFLOPS。
  - 所以 1 TFLOP 的实际耗时不是 1 毫秒，而是 **单核跑 1 TFLOP 的时间**，可能高达 **数秒到数十秒**。

（2）从“延迟”角度看：单次运算的延迟是硬门槛

- 标称算力给出的是 **“每秒钟完成多少次运算”**（吞吐），但它**不承诺单次运算多快完成**（延迟）。
- 在串行算法里，总时间 = **单步延迟 × 步数**，而不是 **总运算量 / 峰值吞吐**。
- 举例：  
  - 假设每步依赖上一步，做 10⁹ 步，每步只做 1000 次浮点运算。  
  - 总运算量 = 10¹² FLOP。  
  - 但每步的**延迟**（从输入到输出）可能是 **微秒级**（因为要访存、同步、流水线冲刷）。  
  - 10⁹ 步 × 1 微秒 = **1000 秒**，远超毫秒级。

### 1.3

| 执行层次 | 软件含义 | 对应硬件 | 直接可用的存储 | 同步与通信手段 |
|---|---|---|---|---|
| **thread** | kernel 的最小执行单位 | 计算单元上的一个 lane | 自己的寄存器 | （自身天然有序） |
| **warp** | 同一时刻执行同一条指令的一组 thread | 调度器管辖的一组 CUDA Core（一个 warp scheduler） | 寄存器文件（各 thread 私有，但 warp 内可经 shuffle 指令交换） | **隐式 SIMD 同步**（同 warp 内指令步调一致）；显式可用 `__shfl_*` 进行 warp 内数据交换 |
| **block** | 一组协作的 thread，可共享内存并同步 | 一个 SM（流式多处理器）上的 resident 线程块 | **共享内存（Shared Memory）** + L1 cache | **`__syncthreads()`** 同步块内所有 thread；通过共享内存通信 |
| **CTA**（Cooperative Thread Array） | 与 **block** 是同一概念（不同厂商/文献的叫法），软件上表示协作线程组 | 同 block，映射到一个 SM | 同 block（共享内存 + L1） | 同 block（`__syncthreads()` + 共享内存） |
| **grid** | 一个 kernel 启动时包含的所有 block 的集合 | 整个 GPU 设备（所有 SM 共同处理） | **全局内存（Global Memory）** + 常量/纹理内存 | **`__threadfence()` 系列** + 原子操作（用于 grid 内跨 block 通信）；**核函数启动/结束**作为隐式全局同步点 |

**补充说明几点（方便理解）：**

1. **warp 的存储**：虽然 warp 内 thread 各有私有寄存器，但 NVIDIA 提供了 `warp shuffle` 指令，允许同一 warp 内直接在线程之间交换数据，无需走共享内存，因此表中写了“可经 shuffle 指令交换”。

2. **CTA 与 block**：在 NVIDIA 文档中 CTA 就是 block 的同义词（源自 PTX 术语），所以软硬件对应完全一致。如果你愿意，也可以把 CTA 行合并，但分开列是为了体现“不同文献叫法”。

3. **grid 的同步**：CUDA 本身不提供 grid 内所有 block 的全局同步屏障（barrier），只能靠 kernel 结束作为天然同步，或者用原子操作 + 全局内存做“自旋同步”（但容易死锁，需谨慎）。

### 1.4 

SIMD = 数据级并行的执行方式；SIMT = 线程级并行的调度模型 + SIMD 执行。

独立 PC ≠ 免费分支。它只解耦了线程间的同步依赖，但不同路径仍需分时执行，代价照付，甚至可能因不收敛而放大。

## 2. 第一个 CUDA 程序

### 2.2

基于 CUDA 编程模型，这五个场景对应的正确修饰符（以及必要的内存空间限定符）如下：

**(a) 在 GPU 上执行、由 CPU 侧启动的 kernel 函数。**
**修饰符：`__global__`**
- 说明：这是 CUDA 中定义 kernel 的标准修饰符，函数返回类型必须是 `void`，且通过 `<<<...>>>` 语法从主机端启动。

**(b) 只会被 kernel 调用的辅助函数。**
**修饰符：`__device__`**
- 说明：该函数在设备端（GPU）编译和执行，且**只能**从其他 `__device__` 或 `__global__` 函数中调用。

**(c) host 和 device 代码都要调用的小工具函数。**
**修饰符：`__host__ __device__`**
- 说明：同时使用两个修饰符，编译器会分别为 CPU 和 GPU 生成两份该函数的代码，从而在两端均可调用。常用作内联小函数（可配合 `#pragma unroll` 或 `__forceinline__` 优化）。

**(d) 整个 kernel 运行期间不变、所有线程都要读的系数表。**
**修饰符/限定符：`__constant__`**
- 说明：使用 `__constant__` 定义常量内存，数据驻留在设备端只读缓存中，对所有线程可见且访问延迟低。需通过 `cudaMemcpyToSymbol` 从主机端初始化。

**(e) block 内线程共享的暂存数组。**
**限定符：`__shared__`**
- 说明：在 kernel 内部或全局使用此限定符声明数组。该数组被分配到每个 block 的共享内存（L1 缓存）中，同 block 内的线程可通过该内存进行低延迟通信和同步。

**补充提示（容易混淆的点）：**
- `__managed__` 可用于声明可直接在 host/device 间自动迁移的变量，但本题 (d) 强调“只读且不变”，更适合用 `__constant__` 以利用缓存加速。
- 如果 (e) 数组大小在编译时未知（动态分配），需在 kernel 启动时指定第三个执行配置参数，并在声明时使用 `extern __shared__` 语法。

### 2.3

`cudaMallocManaged` 是 CUDA 中的统一内存（Unified Memory）分配函数，它分配的内存指针既可在 CPU 上使用，也可在 GPU 上使用，由 CUDA 运行时系统自动管理数据在主机和设备之间的迁移。

(a) Kernel 启动是异步的。`vectorAdd<<<blocks, threads>>>(...)` 只是把 kernel 加入 GPU 的命令队列就立即返回，CPU 继续执行后续代码，此时 kernel 可能还没开始执行，更别提结果数据 c 已经写好了。如果 CPU 不等待 GPU 完成就直接读取 c，会读到未完成的数据（可能是旧值、部分写好的值、或未迁移到 CPU 内存的数据），导致校验和不正确。

### 2.4 

(a) 错误

**理由**：`vectorAdd<<<...>>>(...)` 是**异步**的，它只是把 kernel 启动命令放入 GPU 的命令队列后立即返回，CPU 继续执行后续代码，此时 kernel 可能还没开始执行，更不可能已经执行完毕。

(b) 正确

**理由**：在同一个 CUDA stream 中，所有命令（包括 kernel 和 `cudaMemcpy`）按**提交顺序**串行执行。`cudaMemcpy`（默认是同步版本）会阻塞 CPU，直到 GPU stream 中它前面的所有命令（包括 kernel）执行完毕后，才开始执行拷贝操作。因此可以保证拷贝开始时 kernel 已完成。

(c) 错误

**理由**：Kernel 内部的非法访存（如越界、未对齐等）是**运行时错误**，只有在 GPU 实际执行到该指令时才会发生。`CUDA_CHECK_KERNEL()` 仅检查 kernel 启动时的参数错误（如配置错误），无法捕获运行时的非法访存。错误状态会通过后续的同步调用（如 `cudaDeviceSynchronize()` 或 `cudaMemcpy`）返回给 CPU。

### 2.5

| 宏 | 用途 | 关键设计 |
|----|------|----------|
| `CUDA_CHECK(call)` | 检查同步 CUDA API 的返回值 | 直接捕获返回值，即时报错 |
| `CUDA_CHECK_KERNEL()` | 检查 kernel 启动和执行 | `cudaGetLastError()` 查启动错误 + `cudaDeviceSynchronize()` 查运行时错误 |
